### Рендер и время загрузки

Существующий `e2e/perf.spec.ts` сообщил:

- stress RAF: **60.125 FPS**, 40 башен, **143 врага в конце замера**, max 39 draw calls, 72 180 triangles на момент снимка;
- меню: **117 мс**; меню → кампания → бой ready: **1380 мс** суммарно;
- baseline WebGL перед рестартами: **53 geometries / 0 textures / 8 calls**;
- после 3 рестартов: **53 geometries / 0 textures / 8 calls**;
- JS heap после GC: **10.328834 → 12.316070 MB**, рост **19.24%**.

**Важно:** тест памяти зелёный только из-за своего дополнительного допуска 1.5 MB. Строгая цель пакета «≤ 10%» этим замером **не выполнена**. Это исходное отклонение, а не регрессия нового стека; разобраться до итоговой приёмки S7.

**Ограничения существующего perf:** он проверяет ≥ 150 врагов только перед замером, после этого враги погибают; RAF FPS не доказывает рендер всех кадров; readiness наступает до полной готовности GLB; статистика renderer достаточна для одного прохода, но не для composer. Таким образом, 60.125 FPS — наблюдение исходного сценария, а не доказательство устойчивых 150 врагов со всеми эффектами. Повторять на новом стеке надо с протоколированием GPU, диапазона нагрузки и накоплением draw calls полного кадра. На реальном Android замер пока не проводился.

Asset-complete API пока отсутствует: наличие сетевых ответов не доказывает окончание обработки GLB. Это диагностическая проверка холодной локальной загрузки, не мобильный 4G TTI.
- **Память через CDP**, отдельный test-preview проход, пустой бой; каждый снимок после network-idle + 1 с + `HeapProfiler.collectGarbage`: **6 457 320 → 7 463 964 → 7 708 308 → 7 979 084 bytes** (исходный бой и 3 рестарта). **+23.57%**, монотонный рост; во всех четырёх снимках 53 geometries / 0 textures / 8 calls. Эти замеры уточняют baseline, но не принимают существующие отклонения как новую норму. QA-аудит также выявил риск debug `loadReplay` (начальные overrides/config и подписки старого боя); сохраняем как отдельный риск для проверки replay-паритета при интеграции, golden не меняем.

## Исходные проблемы и риски

1. Память +19.24% при зелёном perf-тесте с дополнительным допуском — не соответствует строгим 10%; нужна честная стабилизация/оценка ownership в S7.
2. Профиль quality существует, но ещё не подключён к сцене; `?quality=low` не доказывает низкое качество.
3. RAF непрерывный; время стрелок/спиннеров и частиц считается разными способами; context loss лишь предотвращает финальный render. Нужен единый lifecycle при интеграции.
4. Поздние GLB-загрузки не имеют полного cleanup, материалы/текстуры загрузчика теряются; ошибки GLB скрываются fallback. Исправление входит в миграцию, не в baseline.
5. HUD находится в общей сцене, не все его материалы отключают depthWrite: N8AO требует визуальной проверки и правильного depth/order.
6. Steiger: cross-import level в `battle/model/levelConfig.test.ts`, `battle/store/battleSession.test.ts`, `battle/store/battleSession.ts`, `progress/store/progressStore.ts`; два предупреждения cross-import tower в battleSession и его тесте; app/ui и два сегмента store. Это исходные находки, не блокирующий DoD линтер; попутный FSD-рефакторинг не делаем.
